Optimization Guide

Recommendations for improving retrieval quality, ordered by payoff-to-effort.

System today: 3,595 books → 1.81M chunks · all-MiniLM-L6-v2 (384-dim) · IVFFlat (nlist 1000, nprobe 50) · 2.8 GB index. The crash and speed are solved — this is about getting the right passages back, plus housekeeping that makes future changes cheap.
Tier 1 Quick wins — hours, high impact

1. Cosine similarity (normalize + inner product) Implemented

MiniLM is trained for cosine, but the old index used un-normalized L2, letting vector magnitude distort ranking. Embeddings are now L2-normalized and indexes built with inner product, so scores are true cosine in [-1, 1]. Set Distance metric → Cosine on the Tuning tab and rebuild to apply it to your current index (seconds, no re-embed).

2. Fix silent chunk truncation Implemented

Chunks were 256 words, but MiniLM's tokenizer caps at 256 subword tokens (~1.3 per word), so the model dropped ~25% of every chunk before embedding. Chunk size is now 200 words to stay under the limit. Takes effect on the next full re-embed.

3. Tune the IVF grid

At 1.8M vectors the rule of thumb is nlist ≈ 4·√N ≈ 5,400 — more, smaller clusters hit the same recall while scanning fewer vectors. Rebuild with nlist 4096 on the Tuning tab, then drag nprobe to find the knee (likely 16–32 for ≥98%).

Tier 2 Bigger quality levers — a day each

4. Persist full chunk text Gap

Metadata stores only a 200-character preview; the full passage text isn't saved anywhere. For a RAG that feeds an LLM, this is the critical gap — you can find a hit but can't hand the model the full passage. Store full chunk text keyed by chunk id (SQLite or parquet). This also unlocks reranking (#5).

5. Add a cross-encoder reranker

Retrieve top-50 from FAISS, then re-score with a cross-encoder that reads query + passage together (BAAI/bge-reranker-base). Usually the largest precision jump in a RAG pipeline. ~50–150 ms per query, only on candidates.

6. Hybrid search (dense + BM25)

Dense embeddings miss exact terms — proper nouns, titles, rare jargon. A book library is full of those. Add SQLite FTS5 (built in) or rank_bm25 and fuse with dense results via Reciprocal Rank Fusion.

7. Move metadata out of an 851 MB JSON

The whole metadata file loads into RAM on every startup, with linear-scan lookups. A SQLite table keyed by chunk id gives O(1) lookups and low memory — the same store you'd use for #4 and #6.

Tier 3 Bigger bets — if quality still matters

8. Upgrade the embedding model

At the same 384 dims (index size unchanged), BAAI/bge-small-en-v1.5 and thenlper/gte-small rank well above MiniLM on MTEB. bge-base-en-v1.5 (768d) is better still but doubles size. bge/e5 need a query prefix. Cost: a full re-embed — cheap if you've done #9.

9. Cache extracted text

PDF extraction is the 13-hour bottleneck; embedding is only ~40 min. Nothing currently persists extracted text, so every model or chunking experiment re-pays the 13 hours. Cache it once and re-embedding becomes a 40-minute job. This is what makes everything else iterable.

10. Incremental indexing

Adding one book currently means a full rebuild. Use IndexIDMap + add_with_ids with a manifest of indexed files, so new books append and removed books get filtered.

11. Memory-map the index

2.8 GB loads fully into RAM at startup. faiss.read_index(path, faiss.IO_FLAG_MMAP) maps it instead — lighter footprint on a laptop, negligible speed cost for IVFFlat.

Measure The meta-recommendation

You can't optimize what you don't measure, and "98.6% recall" is recall against Flat, not against the right answer. Build a small gold set — 30–50 real questions, each tagged with the passage that should win — and script recall@k and MRR. Then every change becomes a number, not a guess.

Suggested order: #1 + #2 (done) → build the eval set → #9 (unlocks iteration) → #4 + #7 + #5 (the RAG-quality core) → re-measure → decide on #8.
